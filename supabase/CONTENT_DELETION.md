# Permanent post and event deletion

Apply `migrations/20261026042428_permanent_content_deletion.sql` after the existing migrations. The authenticated `/api/orbit` route validates strict `delete_post` / `delete_event` actions and uses the existing mutation RPC. PostgreSQL derives the actor from `auth.uid()` and checks the record owner. Club event deletion additionally requires current club ownership and follower access. Home/profile posts remain author-owned across workspace changes; club chat messages cannot be deleted through the post action. Already absent records are successful, idempotent deletions.

Foreign keys permanently cascade likes, comments, nested replies, comment likes, RSVPs, event choices and post attachment metadata. No deleted content is kept for recovery. Event Home Feed cards are generated from the same event row and disappear with it. Unrelated club posts, chat, listings and files are untouched.

Post attachments use exclusive IDs and paths. The deletion transaction first saves only their owner/ID/path in a private cleanup queue, then deletes the post and its dependent metadata. The server removes those binaries through the authenticated **Storage API**, never SQL. Added Storage policies allow an owner to select/delete only their queued files; live attachments retain their existing permissions. An acknowledgement removes a queue entry only when Storage metadata confirms the binary is gone. Failed or partial removal, lost responses and process crashes leave retry jobs intact. Pending paths cannot be reused for new attachments.

The next normal authenticated `/api/orbit` load or mutation retries up to 16 queued files. The existing visible-page polling and future sign-ins therefore retry cleanup without a worker, privileged key, new dependency or scheduled service. If an author never returns after an outage, their pending files remain private until a retry. Previously issued short-lived download URLs retain their original expiry until the object is removed. The UI reports pending cleanup and does not restore the deleted post.

A session-local set of successfully deleted IDs prevents older in-flight responses and cached feed/profile/club pages from redisplaying cards. Database absence remains authoritative after refresh, workspace switching or a new session. Confirmation dialogs require an explicit Delete action; cancellation and failures retain the original content. Demo deletions affect fictional local state only and reset when leaving demo mode.
